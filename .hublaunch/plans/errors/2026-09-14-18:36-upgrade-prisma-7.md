# Upgrade to Prisma 7: move the datasource URL to `prisma.config.ts` and use the `pg` driver adapter

## Plan Summary

- **What/why**: Upgrade the project from Prisma 6.19.3 to Prisma 7.10.0 so `prisma/schema.prisma` no longer carries `url = env("DATABASE_URL")`. That line is what the VS Code Prisma extension (v31.12.8, which enforces Prisma 7 schema rules) flags in the Problems panel with: `The datasource property 'url' is no longer supported in schema files…`. Nothing is broken at runtime today; the diagnostic is a tooling/version mismatch, and the real fix is the upgrade the message asks for.
- **Key decisions**: (1) Upgrade to Prisma 7 rather than downgrading the editor extension. (2) Pin `prisma` and `@prisma/client` to `^7.10.0` explicitly, because the `prisma` CLI's npm `latest` dist-tag currently resolves to an **8.0.0 release candidate**. (3) Switch the generator to the new `prisma-client` provider (the `prisma-client-js` provider is deprecated in 7). (4) Use `@prisma/adapter-pg` for every environment (Docker locally, Neon / Vercel Postgres in production); Accelerate is not used. (5) In `prisma.config.ts` read `process.env.DATABASE_URL` directly instead of Prisma's `env()` helper, because `env()` throws at config-load time when the variable is unset, which would break `prisma generate` in `postinstall` on a fresh clone before `.env` exists.
- **Most important files**: `prisma/schema.prisma`, new `prisma.config.ts`, `src/server/db.ts`, `prisma/seed.ts`, `package.json`.
- **Priority/complexity**: Medium priority (editor diagnostic today, but Prisma 6 is now the previous major and the upgrade is inevitable), Medium complexity (small diff, but touches install/build/migrate/seed plumbing that must be verified end to end).

## Problem Statement

VS Code shows a Problems-panel diagnostic on `prisma/schema.prisma` line `url = env("DATABASE_URL")`:

```
The datasource property `url` is no longer supported in schema files. Move connection URLs for Migrate to `prisma.config.ts` and pass either `adapter` for a direct database connection or `accelerateUrl` for Accelerate to the `PrismaClient` constructor. See https://pris.ly/d/config-datasource and https://pris.ly/d/prisma7-client-config
```

The project's installed `prisma` and `@prisma/client` are both **6.19.3**, which still accept `url` in the schema, so the app, migrations, and seed all work today. The diagnostic comes from the VS Code Prisma extension's bundled language server, which now follows Prisma 7 rules. Silencing it properly means completing the Prisma 7 upgrade.

### Planning Context

**Key Requirements Discussed:**

- The fix must be the real Prisma 7 upgrade, not a per-machine workaround (downgrading the VS Code extension was considered and rejected).
- Local dev uses Docker Postgres (`docker-compose.yml`); production uses Neon or Vercel Postgres via a plain Postgres connection string. Prisma Accelerate is not used anywhere, so the `adapter` constructor path applies, not `accelerateUrl`.
- The generated client stays git-ignored (`/generated` in `.gitignore`) and is regenerated by the `postinstall` and `build` scripts, exactly as today.
- `README.md` and `ralph.md` must be updated so setup docs match the new mechanics.

**Decisions Made:**

- **Pin `^7.10.0`, not "latest".** `npm view prisma dist-tags` shows `latest: 8.0.0-rc.15` and `prev: 7.10.0` for the CLI, while `@prisma/client` `latest` is `7.10.0`. Installing "latest" would produce a CLI/client mismatch on a release candidate. All three Prisma packages (`prisma`, `@prisma/client`, `@prisma/adapter-pg`) are pinned to `^7.10.0`.
- **Switch generator to `prisma-client`.** Prisma 7 deprecates `prisma-client-js` ("will be removed in future releases"). The new generator emits plain TypeScript into the `output` directory and the client is imported from `<output>/client`. Verified in a scratch project with this repo's `tsconfig.json` settings (`moduleResolution: "Bundler"`, `verbatimModuleSyntax: true`, `"type": "module"`): `prisma generate` writes `generated/prisma/{client.ts, enums.ts, models.ts, internal/, models/, browser.ts, commonInputTypes.ts}`, the generated files import each other extension-less (`from "./enums"`), and `tsc --noEmit` exits 0 with the client imported from `../generated/prisma/client`. No `moduleFormat` / `importFileExtension` overrides are needed.
- **`@prisma/adapter-pg` everywhere.** It works over any standard Postgres connection string, including Neon's pooled URL. `@prisma/adapter-pg@7.10.0` declares `pg@^8.16.3` and `@types/pg@^8.16.0` as its own dependencies, so `pg` does not need to be added separately. `@prisma/adapter-neon` (Neon's serverless HTTP driver) was considered and rejected as unnecessary complexity.
- **`process.env.DATABASE_URL ?? ""` in `prisma.config.ts`, not `env("DATABASE_URL")`.** Verified in the scratch project: with `env("DATABASE_URL")`, running `prisma generate` with the variable unset fails with `Failed to load config file … PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL`. The repo's `postinstall` runs `prisma generate`, and the README's setup order is `pnpm install` **before** `cp .env.example .env`, so a fresh clone would fail to install. With `process.env.DATABASE_URL ?? ""`, `prisma generate` succeeds without the variable, and `prisma migrate status` reports the clear error `Error: Connection url is empty. See https://pris.ly/d/config-url` — an acceptable failure mode for commands that genuinely need a database.
- **Keep `generated/` git-ignored.** Committing the generated TypeScript was considered; keeping the existing regenerate-on-install pattern avoids churn and large diffs.

**Out of Scope:**

- Downgrading or pinning the VS Code Prisma extension.
- Committing `generated/prisma`.
- Any change to `prisma/migrations/`, the Prisma models, or the SQL in `src/server/campaignStats.ts`.
- Prisma 8 (still a release candidate).
- Adopting `@prisma/adapter-neon` or Prisma Accelerate.
- The untracked `pnpm-workspace.yaml` in the repo root (it contains placeholder `allowBuilds` text generated by pnpm and is not part of this change).

### Background & Context

- **Why needed**: Prisma 7 moved all CLI connection configuration out of the schema into `prisma.config.ts`, and `PrismaClient` now requires an explicit driver adapter (or Accelerate URL) instead of an embedded Rust query engine reading `url` from the schema. Editor tooling already assumes this layout.
- **Current state**: Prisma 6.19.3; `prisma/schema.prisma` has `url = env("DATABASE_URL")` and the `prisma-client-js` generator with `output = "../generated/prisma"`; `src/server/db.ts` and `prisma/seed.ts` call `new PrismaClient()` with no adapter; seeding is configured by the `"prisma": { "seed": "tsx prisma/seed.ts" }` key in `package.json`; there is no `prisma.config.ts`.
- **Who is affected**: every developer opening the schema in VS Code (persistent diagnostic), and the project as a whole once Prisma 6 stops receiving updates.

**Current Behavior**:

- VS Code Problems panel shows the `url` diagnostic on `prisma/schema.prisma`.
- Runtime, migrations, and seed work on Prisma 6.19.3.

**Desired Behavior**:

- No Prisma diagnostics in VS Code.
- Project on Prisma 7.10.0 with `prisma.config.ts`; `pnpm install`, `pnpm build`, `pnpm db:generate`, `pnpm db:migrate`, `pnpm db:seed`, `pnpm dev`, `pnpm donate`, `pnpm typecheck`, and `pnpm test` all behave exactly as before.

## Detailed Requirements

### Functional Requirements

1. **Schema**
   - `prisma/schema.prisma` datasource block contains only `provider = "postgresql"` (no `url`).
   - Generator block uses `provider = "prisma-client"` and keeps `output = "../generated/prisma"`.
   - Models and the header comment are unchanged.

2. **CLI configuration**
   - New root file `prisma.config.ts` provides the schema path, migrations path, seed command, and datasource URL to the Prisma CLI.
   - It loads `.env` via `dotenv/config` (Prisma 7 no longer auto-loads `.env`).
   - It must not throw when `DATABASE_URL` is unset, so `prisma generate` keeps working in `postinstall`.

3. **Client construction**
   - `src/server/db.ts` and `prisma/seed.ts` construct `PrismaClient` with `adapter: new PrismaPg({ connectionString })`.
   - `src/server/db.ts` sources the connection string from the validated `env.DATABASE_URL` (`src/env.js`); `prisma/seed.ts` sources it from `process.env.DATABASE_URL` after importing `dotenv/config`.
   - The dev-mode `globalThis` singleton pattern in `src/server/db.ts` is preserved.

4. **Package scripts and dependencies**
   - `prisma`, `@prisma/client` bumped to `^7.10.0`; `@prisma/adapter-pg@^7.10.0` added to `dependencies`.
   - The `"prisma": { "seed": … }` key is removed from `package.json` (moved to `prisma.config.ts`).
   - All existing `scripts` entries keep their current names and commands.
   - Edge case: `pnpm install` on a machine with no `.env` must still succeed (postinstall `prisma generate`).
   - Edge case: `pnpm db:migrate` with no `DATABASE_URL` must fail with Prisma's `Connection url is empty` error rather than a TypeScript config-load stack trace.

5. **Documentation**
   - `README.md` and `ralph.md` describe `prisma.config.ts`, the seed location, and the adapter.

### Technical Requirements

- **Technology**: Prisma 7.10.0 (`prisma`, `@prisma/client`, `@prisma/adapter-pg`), `pg` 8.x (transitive), Next.js 16.3.4, TypeScript 5, ESM (`"type": "module"`), pnpm 12.
- **Location**: `prisma/schema.prisma`, `prisma.config.ts` (new, repo root), `src/server/db.ts`, `prisma/seed.ts`, `package.json`, `pnpm-lock.yaml`, `README.md`, `ralph.md`.
- **Dependencies**: `dotenv` is already a devDependency (`^17.4.2`) and is already used by `scripts/donate.ts` line 11; `tsx` is already a devDependency and runs the seed.
- **Constraints**: `generated/` stays git-ignored; `tsconfig.json` `exclude` already lists `generated`, so generated files are type-checked only transitively via imports (verified to pass).

### Non-Functional Requirements

- **Performance**: `@prisma/adapter-pg` uses a `pg.Pool`. Prisma 7's adapter pool defaults differ from Prisma 6's built-in pool (idle timeout 10s vs 300s; connection timeout 0 vs 5s). No tuning is required for this app's load; the defaults are accepted.
- **Security**: `DATABASE_URL` continues to live only in `.env` (git-ignored) and Vercel env vars. `prisma.config.ts` must never log or hard-code the connection string.
- **Backwards Compatibility**: No migration files change; `prisma migrate deploy` applies the existing `20260901122036_init` migration unchanged. The public API of `src/server/db.ts` (`export const db`) is unchanged, so `donations.ts`, `campaignStats.ts`, `api/trpc.ts`, `app/c/[slug]/page.tsx`, and `scripts/donate.ts` need no edits.
- **Error Handling**: Missing `DATABASE_URL` at app runtime is still caught by `src/env.js` (`z.string().url()`), before the adapter is constructed.

## Proposed Solution

**High-level approach**: Perform the official Prisma 6 → 7 upgrade in one PR: bump packages, add `prisma.config.ts`, strip `url` from the schema, switch the generator, and pass a `PrismaPg` adapter to both `PrismaClient` constructors. Then verify install, typecheck, tests, migrate, seed, the campaign page, and the raw snapshot query.

```
prisma.config.ts ──▶ prisma CLI (generate / migrate / db seed / studio)
   │ reads .env via dotenv/config, exposes datasource.url + migrations.seed
   ▼
prisma/schema.prisma (no url; generator "prisma-client") ──▶ generated/prisma/client.ts
                                                                     │
src/server/db.ts ── new PrismaClient({ adapter: new PrismaPg({ connectionString: env.DATABASE_URL }) })
prisma/seed.ts   ── new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })
```

### Key Components

1. **`prisma.config.ts` (new)**
   - Central CLI configuration required by Prisma 7.
   - Reads `process.env.DATABASE_URL` directly (see Decisions) so `prisma generate` works without a database URL.
   - Carries the seed command that used to live in `package.json`.

2. **`prisma/schema.prisma`**
   - Remove `url`; change generator provider. Keep everything else byte-for-byte.

3. **`PrismaClient` construction (`src/server/db.ts`, `prisma/seed.ts`)**
   - Add `PrismaPg` adapter. Import the client from `generated/prisma/client` (new generator layout).

4. **`package.json` / lockfile**
   - Version bumps, new adapter dependency, seed key removal.

5. **Docs (`README.md`, `ralph.md`)**
   - Reflect the new config file and unchanged commands.

### Files Likely to Change

- `prisma/schema.prisma` — remove `url = env("DATABASE_URL")`; `provider = "prisma-client"`.
- `prisma.config.ts` — **new**; CLI config (schema, migrations, seed, datasource url).
- `src/server/db.ts` — import from `../../generated/prisma/client`; add `PrismaPg` adapter.
- `prisma/seed.ts` — import `dotenv/config`; import from `../generated/prisma/client`; add `PrismaPg` adapter.
- `package.json` — bump `prisma`/`@prisma/client` to `^7.10.0`; add `@prisma/adapter-pg@^7.10.0`; delete the `prisma.seed` key.
- `pnpm-lock.yaml` — regenerated by `pnpm install`.
- `README.md` — setup/scripts/env/deploy/project-structure sections.
- `ralph.md` — setup section.

### Code Patterns to Follow

**Pattern References:**

- **For loading `.env` in a standalone script**: follow [`scripts/donate.ts`](scripts/donate.ts) line 11 (`import "dotenv/config";` as the first import). Apply the same line at the top of `prisma.config.ts` and `prisma/seed.ts`.
- **For the dev-mode Prisma singleton**: keep the existing structure of [`src/server/db.ts`](src/server/db.ts) lines 4–16 (`createPrismaClient` factory, `globalForPrisma` cache, `env.NODE_ENV` guard). Only the import path and the constructor options change.
- **For reading validated env vars on the server**: use `env.DATABASE_URL` from [`src/env.js`](src/env.js) line 10, as `src/server/db.ts` already does for `env.NODE_ENV`.

**Anti-Patterns to Avoid:**

- Do not use Prisma's `env("DATABASE_URL")` helper in `prisma.config.ts` — it throws at config load when the variable is missing and breaks `postinstall` (verified).
- Do not construct a second `pg.Pool` or a second `PrismaClient` anywhere else; all app code must keep importing `db` from `~/server/db`.
- Do not add `moduleFormat`, `runtime`, or `importFileExtension` to the generator block — the inferred defaults are verified to work with this repo's tsconfig, and explicit `importFileExtension = "ts"` would trip `tsc` (TS5097) without `allowImportingTsExtensions`.
- Do not install `prisma@latest` (currently an 8.0 RC).
- Do not commit `generated/` or `.env`.

### 6. Edge Cases & Considerations

#### Edge Cases to Handle

1. **`pnpm install` with no `.env`** (fresh clone, CI, Vercel install step): `postinstall` → `prisma generate` must succeed. Guaranteed by `process.env.DATABASE_URL ?? ""` in `prisma.config.ts` (verified: generate succeeds with the variable unset).
2. **`pnpm db:migrate` / `pnpm db:seed` with no `DATABASE_URL`**: Prisma prints `Error: Connection url is empty. See https://pris.ly/d/config-url` and exits non-zero. This is the intended, actionable failure.
3. **`DATABASE_URL` set but database down**: `prisma migrate deploy` fails with `P1001: Can't reach database server`; the app's first query fails with the same code. Unchanged from Prisma 6 behavior.
4. **Vercel build**: Vercel injects `DATABASE_URL` into `process.env`, so `dotenv/config` is a no-op and `prisma migrate deploy` in `build` works. `dotenv` is a devDependency; Vercel installs devDependencies during build, and `prisma.config.ts` is only evaluated by the CLI, never by the deployed app.
5. **Unit tests**: `vitest.config.mts` sets `SKIP_ENV_VALIDATION=1`; no test imports `~/server/db`, so no adapter is constructed during `pnpm test`. If a future test does import it, `new PrismaPg({ connectionString: undefined })` does not connect eagerly (pg pools are lazy), so import alone remains safe.
6. **Raw SQL bigint columns**: `getSnapshot` casts `SUM`/`COUNT` to `::bigint` and converts with `Number()`. node-postgres returns `bigint`-typed columns as strings by default, but Prisma's `pg` adapter maps them to JS `bigint` for `$queryRaw`, matching the existing `SnapshotRow` type. Phase 3's `pnpm donate` and page-load checks confirm this end to end; if the value ever arrived as a string, `Number()` would still coerce it correctly, so the code is robust either way.

#### Potential Challenges

- ⚠️ **Prisma CLI `latest` is an 8.0 RC**: always install with explicit `^7.10.0` ranges. `pnpm add prisma@latest` would install `8.0.0-rc.15`.
- ⚠️ **Install ordering**: `pnpm install` runs `prisma generate` through `postinstall` using the *new* 7.x CLI. If `prisma/schema.prisma` still contains `url`, that generate fails and the install errors. Phase 1 therefore edits the schema and creates `prisma.config.ts` before `pnpm install`.
- ⚠️ **Generated code type-checking**: `tsconfig.json` excludes `generated`, but files imported from `src/server/db.ts` are still checked transitively. Verified clean with the inferred generator defaults; do not add explicit `importFileExtension`.
- ⚠️ **Import path change**: the new generator's entry point is `generated/prisma/client` (not `generated/prisma`). Both import sites (`src/server/db.ts`, `prisma/seed.ts`) must use the `/client` suffix or resolution fails.

#### Security Considerations

- `DATABASE_URL` is never logged; `prisma.config.ts` must not `console.log` it.
- `.env` remains git-ignored; `prisma.config.ts` is committed and contains no secrets.
- The `pg` driver honours `sslmode` in the connection string; Neon URLs already include `sslmode=require`.
