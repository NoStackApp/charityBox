# Upgrade to Prisma 7: move the datasource URL to `prisma.config.ts` and use the `pg` driver adapter

## Plan Summary

- **What/why**: Upgrade the project from Prisma 6.19.3 to Prisma 7.10.0 so `prisma/schema.prisma` no longer carries `url = env("DATABASE_URL")`. That line is what the VS Code Prisma extension (v31.x, which ships the Prisma 7 language server) flags in the Problems panel as `The datasource property 'url' is no longer supported in schema files…`. Nothing is broken at runtime today; the diagnostic is a version mismatch between the editor tooling and the installed Prisma, and the durable fix is the upgrade the message asks for.
- **Key decisions**: (1) Upgrade to Prisma 7 rather than pin the editor to the Prisma 6 language server. (2) Pin `prisma`, `@prisma/client`, and `@prisma/adapter-pg` to `7.10.0` exactly, because the npm `latest` tag for `prisma` resolves to an 8.0.0 release candidate. (3) Use the `prisma-client` generator (the `prisma-client-js` provider is deprecated in 7), keeping the output at `generated/prisma`; the import path becomes `generated/prisma/client`. (4) Use `@prisma/adapter-pg` (node-postgres) in every environment (Docker Postgres locally, Neon / Vercel Postgres in production). (5) In `prisma.config.ts` read `process.env.DATABASE_URL` and only set `datasource` when it is defined, because Prisma's `env()` helper throws while the config file loads, which would break `prisma generate` in the `postinstall` script on a fresh clone before `.env` exists. (6) Pin `"packageManager": "pnpm@10.28.0"` and commit a valid `pnpm-workspace.yaml` with an `allowBuilds` map, matching the pnpm 10.28 that Vercel uses to build this project.
- **Most important files**: `prisma/schema.prisma`, new `prisma.config.ts`, `src/server/db.ts`, `prisma/seed.ts`, `package.json`, `pnpm-workspace.yaml`.
- **Priority/complexity**: Medium priority (editor diagnostic today; Prisma 6 is now the previous major). Medium complexity (small diff, but it touches install, build, migrate, and seed plumbing that must be verified end to end).

## Problem Statement

The VS Code Prisma extension reports an error on `prisma/schema.prisma` line 11 (`url = env("DATABASE_URL")`): *"The datasource property `url` is no longer supported in schema files. Move connection URLs for Migrate to `prisma.config.ts` and pass either `adapter` for a direct database connection or `accelerateUrl` for Accelerate to the `PrismaClient` constructor."* The project is on Prisma 6.19.3, where that property is still valid, so the app works, but the error is shown to everyone who opens the repo. Upgrading to Prisma 7 removes the property legitimately and moves the project onto the current major.

### Planning Context

**Key Requirements Discussed:**

- The fix must be the real Prisma 7 upgrade, not a per-machine editor workaround (`prisma.pinToPrisma6` in `.vscode/settings.json` was considered and rejected).
- Local dev uses Docker Postgres (`docker-compose.yml`); production uses Neon or Vercel Postgres via a plain Postgres connection string. Prisma Accelerate is not used anywhere, so the `adapter` constructor path applies, never `accelerateUrl`.
- The generated client stays git-ignored (`/generated` in `.gitignore`) and is regenerated by the `postinstall` and `build` scripts exactly as today. It stays in `generated/prisma` (not moved to `src/generated`).
- `README.md` and `ralph.md` must be updated so setup docs match the new mechanics.
- The untracked, invalid `pnpm-workspace.yaml` in the working tree (its `allowBuilds` values are the literal placeholder text `set this to true or false`) must be replaced with a valid file and committed.

**Decisions Made:**

- **Exact-pin 7.10.0** (`"prisma": "7.10.0"`, `"@prisma/client": "7.10.0"`, `"@prisma/adapter-pg": "7.10.0"`) rather than `^7` or `latest`. `npm view prisma dist-tags` resolves `latest` to `8.0.0-rc.15`; an accidental RC install would break the build. `@prisma/adapter-pg` bundles `pg` and `@types/pg` as its own dependencies, so `pg` is **not** added to `package.json` directly.
- **`@prisma/adapter-pg` everywhere**, rather than `@prisma/adapter-neon` in production. Neon's pooled endpoint speaks ordinary Postgres TCP, so one adapter keeps a single code path for Docker dev and Neon prod.
- **`process.env.DATABASE_URL` instead of `env("DATABASE_URL")`** in `prisma.config.ts`. Verified with Prisma 7.10.0: with `env()` the CLI fails to load the config at all (`PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL`) and `prisma generate` exits non-zero when the variable is unset. With the conditional `datasource` shown in Phase 2, `prisma generate` succeeds with no URL, and commands that need one fail with Prisma's own message `The datasource.url property is required in your Prisma config file when using prisma migrate …`.
- **Seed script stays standalone** (constructs its own `PrismaClient` with the adapter) rather than importing `src/server/db.ts`. `db.ts` imports `~/env`, whose schema requires `CLERK_SECRET_KEY` and `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`; importing it from the seed would make `pnpm db:seed` fail on any machine that has only `DATABASE_URL` configured.
- **`db:generate` and `db:push` chain `&& prisma generate`**, because in Prisma 7 `prisma migrate dev` and `prisma db push` no longer regenerate the client automatically.
- **`packageManager` pin to `pnpm@10.28.0`.** Vercel currently builds this project with pnpm 10.28.0 ("Using pnpm@10.x based on project creation date"); the `allowBuilds` setting in `pnpm-workspace.yaml` requires pnpm ≥ 10.26. pnpm 10+ honours the `packageManager` field and switches to the pinned version automatically, so local and CI installs converge on the same pnpm.
- **No change to `src/server/campaignStats.ts`.** Its `$queryRaw` casts `SUM`/`COUNT` to `::bigint` and converts with `Number()`. The `@prisma/adapter-pg` path returns those columns as JS `bigint`, matching the existing `SnapshotRow` type; end-to-end checks in Phase 3 (`pnpm donate`, page load) confirm this.
- **No change to `src/server/donations.ts`, `src/server/api/trpc.ts`, `src/app/c/[slug]/page.tsx`, `scripts/donate.ts`, `src/env.js`, `.env.example`, or anything under `prisma/migrations/`.** The public API of `src/server/db.ts` (`export const db`) is unchanged.

**Out of Scope:**

- Switching to `@prisma/adapter-neon`, Prisma Accelerate, or Prisma Postgres.
- Moving the generated client under `src/`.
- Pinning or configuring the VS Code Prisma extension.
- Any schema/model change or new migration. `prisma migrate dev` must report the schema already in sync.
- Vercel dashboard configuration. The Preview environment's `DATABASE_URL` was added on 2026-09-15 and the Clerk keys are added by the project owner before launch (see section 11). The implementing agent does not touch Vercel.

### Background & Context

- **Why now**: Prisma 7 is the current major. The editor tooling has already moved to it, so the schema shows a permanent error in every editor. Two earlier attempts at this exact upgrade (GitHub issues #5 and #7, PRs #6 and #8, now closed) were functionally correct and passed verification; their Vercel Preview builds failed only because the Vercel Preview environment had no `DATABASE_URL` at the time. That environment gap is closed, so this plan repeats the upgrade cleanly.
- **Current state**: `package.json` pins `prisma` and `@prisma/client` at `^6.19.3`; `prisma/schema.prisma` uses the `prisma-client-js` generator with `output = "../generated/prisma"` and a `url = env("DATABASE_URL")` datasource; `src/server/db.ts` constructs `new PrismaClient({ log })` with no adapter; `prisma/seed.ts` constructs a bare `new PrismaClient()`; the seed command lives in `package.json#prisma.seed`.
- **Who is affected**: every developer who opens the repo in VS Code (red error in Problems), and future maintainers once Prisma 6 stops receiving updates.

**Current Behavior**:

- VS Code shows a severity-8 Prisma error on `prisma/schema.prisma:11`.
- The app, migrations, seed, and build all work on Prisma 6.19.3.

**Desired Behavior**:

- The schema has no `url` property; the editor shows no Prisma diagnostics.
- The project runs on Prisma 7.10.0 with `prisma.config.ts` and the `pg` driver adapter; typecheck, tests, migrate, seed, the demo CLI, the dev server, and `pnpm build` all pass exactly as before.
- A fresh clone works with `pnpm install` (no `.env` needed for the install step), `cp .env.example .env`, `pnpm db:up`, `pnpm db:generate`, `pnpm db:seed`, `pnpm dev`.

## Detailed Requirements

### Functional Requirements

1. **Schema and config**
   - `prisma/schema.prisma` datasource block contains only `provider = "postgresql"`.
   - Generator block is `provider = "prisma-client"` with `output = "../generated/prisma"`.
   - New root file `prisma.config.ts` declares `schema`, `migrations.path`, `migrations.seed`, and (when `DATABASE_URL` is defined) `datasource.url`.
   - `package.json` no longer has a `prisma` field (the seed command moves to `prisma.config.ts`).
   - Edge case: `prisma generate` with `DATABASE_URL` unset must succeed (it runs from `postinstall` on fresh clones and on Vercel's install step).
   - Edge case: `prisma migrate deploy` / `prisma db seed` with `DATABASE_URL` unset must fail with Prisma's own "datasource.url property is required" error, not a stack trace from the config file.

2. **Client construction**
   - `src/server/db.ts` constructs `new PrismaClient({ adapter: new PrismaPg({ connectionString: env.DATABASE_URL }), log })`, imports `PrismaClient` from `../../generated/prisma/client`, and keeps the `globalThis` singleton pattern unchanged.
   - `prisma/seed.ts` loads `dotenv/config`, constructs its own adapter-backed client, imports from `../generated/prisma/client`, and is otherwise unchanged (same slug, same upsert, same output line).

3. **Package management**
   - `pnpm-workspace.yaml` is committed with `allowBuilds` set to `true` for `@prisma/client`, `@prisma/engines`, `esbuild`, and `prisma`.
   - `package.json` has `"packageManager": "pnpm@10.28.0"`.
   - `pnpm-lock.yaml` is regenerated and shows `prisma@7.10.0`, `@prisma/client@7.10.0`, `@prisma/adapter-pg@7.10.0`; no `8.x` Prisma package appears anywhere in it.

4. **Scripts**
   - `db:generate` becomes `prisma migrate dev && prisma generate`; `db:push` becomes `prisma db push && prisma generate`. All other scripts are unchanged (`build` already runs `prisma generate` first).

### Technical Requirements

- **Technology/Framework**: TypeScript 5, Next.js 16.3.4 (Turbopack), Prisma 7.10.0, `@prisma/adapter-pg` 7.10.0 (bundles `pg` 8.x), pnpm 10.28.0, Node ≥ 20.19 (Prisma 7's floor; Vercel builds on Node 24.x).
- **Location**: root (`prisma.config.ts`, `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`), `prisma/` (`schema.prisma`, `seed.ts`), `src/server/db.ts`, docs (`README.md`, `ralph.md`), one new unit test under `src/server/__tests__/`.
- **Dependencies**: `src/server/donations.ts`, `src/server/campaignStats.ts`, `src/server/api/trpc.ts`, `src/app/c/[slug]/page.tsx`, and `scripts/donate.ts` import `db` from `src/server/db.ts` and need no edits.
- **Constraints**: no migration files change; `prisma migrate dev` must report "Already in sync" and create no new migration. `tsconfig.json` (`moduleResolution: "Bundler"`, `verbatimModuleSyntax: true`, `exclude: ["generated"]`) is unchanged; the generated client typechecks under it and `prisma.config.ts` is picked up by the existing `**/*.ts` include.

### Non-Functional Requirements

- **Performance**: `@prisma/adapter-pg` wraps a `pg.Pool`. Prisma 7's adapter pool defaults differ from Prisma 6's built-in pool (idle timeout 10 s vs 300 s; connection timeout 0 vs 5 s). No tuning is needed for this app's load; defaults are accepted.
- **Security**: `DATABASE_URL` continues to live only in `.env` (git-ignored) and Vercel env vars. `prisma.config.ts` must never log or hard-code the connection string.
- **Backwards Compatibility**: the existing `20260901122036_init` migration applies unchanged. The exported `db` symbol and all model/raw query calls behave identically.
- **Error Handling**: missing `DATABASE_URL` at app runtime is still caught by `src/env.js` (`z.string().url()`) before the adapter is constructed. Missing `DATABASE_URL` for a CLI command surfaces Prisma's "datasource.url property is required" error.

## Proposed Solution

**High-level approach**: perform the standard Prisma 6 → 7 migration for a PostgreSQL project: bump the three Prisma packages to 7.10.0, add `prisma.config.ts`, strip `url` from the schema, switch the generator provider, pass a `PrismaPg` adapter to every `PrismaClient`, and align the package manager configuration with what Vercel already uses. Then verify install, typecheck, tests, migrate, seed, CLI, dev server, and production build end to end.

```
 pnpm install ──▶ postinstall: prisma generate ──▶ generated/prisma/client.ts
                       │ (reads prisma.config.ts; no DATABASE_URL needed)
 pnpm build ───▶ prisma generate ──▶ prisma migrate deploy ──▶ next build
                                        │ (DATABASE_URL via prisma.config.ts)
 app runtime ──▶ src/server/db.ts ──▶ PrismaClient({ adapter: PrismaPg(env.DATABASE_URL) })
 pnpm db:seed ─▶ prisma.config.ts migrations.seed ──▶ tsx prisma/seed.ts (own PrismaPg client)
```

### Key Components

1. **`prisma.config.ts` (new, repo root)**
   - Owns schema path, migrations path, seed command, and the datasource URL for all `prisma` CLI commands. Imports `dotenv/config` because the Prisma 7 CLI no longer loads `.env` on its own.
   - Sets `datasource` only when `process.env.DATABASE_URL` is defined so `prisma generate` works without it.
   - Never imported by application code.

2. **`prisma/schema.prisma`**
   - Remove the `url` line; switch `provider = "prisma-client-js"` to `provider = "prisma-client"`. Output path and all models unchanged.

3. **`src/server/db.ts`**
   - Add the `PrismaPg` adapter and update the import path. The singleton and `log` configuration stay the same.

4. **`prisma/seed.ts`**
   - Same adapter treatment as `db.ts`, plus `import "dotenv/config"` because the Prisma 7 CLI no longer injects `DATABASE_URL` into the seed process.

5. **Package management (`package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`)**
   - Version bumps, `packageManager` pin, removal of `package.json#prisma`, script chaining, valid `allowBuilds` map.

6. **Docs (`README.md`, `ralph.md`) and one unit test**
   - Setup docs mention `prisma.config.ts`; a small Vitest file guards the config's shape.

### Files Likely to Change

- `package.json` - Prisma versions, `@prisma/adapter-pg`, `packageManager`, remove `prisma.seed`, chain `db:generate` / `db:push`.
- `pnpm-workspace.yaml` - replace placeholder text with a valid `allowBuilds` map; commit it (currently untracked).
- `pnpm-lock.yaml` - regenerated by `pnpm install`.
- `prisma.config.ts` - **new**.
- `prisma/schema.prisma` - generator provider, remove `url`.
- `src/server/db.ts` - adapter + import path.
- `prisma/seed.ts` - dotenv + adapter + import path.
- `src/server/__tests__/prismaConfig.test.ts` - **new** unit test.
- `README.md`, `ralph.md` - documentation.

### Code Patterns to Follow

**Pattern References:**

- **For the client singleton**: keep the structure in [`src/server/db.ts`](src/server/db.ts) lines 4-16 (a `createPrismaClient` factory, a `globalForPrisma` cache, and the `NODE_ENV !== "production"` guard). Only the import path and the `adapter` option change.
- **For loading `.env` in a standalone script**: follow [`scripts/donate.ts`](scripts/donate.ts) line 11 (`import "dotenv/config";` as the first import). Apply the same line to `prisma/seed.ts`.
- **For the seed's lifecycle**: keep the `main().then(disconnect).catch(log, disconnect, exit 1)` shape in [`prisma/seed.ts`](prisma/seed.ts) lines 50-58 unchanged.
- **For unit tests**: follow the plain `describe`/`it`/`expect` style in [`src/server/__tests__/donations.test.ts`](src/server/__tests__/donations.test.ts) lines 1-10 (Vitest globals are enabled in `vitest.config.mts`, but the existing files import from `vitest` explicitly; do the same).

**Anti-Patterns to Avoid:**

- Do **not** use `env("DATABASE_URL")` from `prisma/config` in `prisma.config.ts`. It throws while the config loads and breaks `prisma generate` on machines without the variable (verified on 7.10.0).
- Do **not** install `prisma@latest`, `@prisma/client@latest`, or `^7` ranges that could float. `latest` is an 8.0 release candidate; pin `7.10.0` exactly.
- Do **not** import `PrismaClient` from `@prisma/client` or from `../../generated/prisma` (no `/client` suffix). With the `prisma-client` generator the entry point is `generated/prisma/client`.
- Do **not** add `pg` to `package.json`; `@prisma/adapter-pg` already depends on it.
- Do **not** import `src/server/db.ts` from `prisma/seed.ts` (it drags in the Clerk env requirements).
- Do **not** create a new migration; if `prisma migrate dev` proposes one, the schema was edited incorrectly.
- Do **not** put `onlyBuiltDependencies` under a `pnpm` key in `package.json`; pnpm 10.28+ ignores that key and warns. The `allowBuilds` map in `pnpm-workspace.yaml` is the supported location.

### Phase 2: Prisma 7 configuration and code changes

- [ ] **Create `prisma.config.ts`** at the repo root with exactly:

  ```ts
  // Prisma 7 CLI configuration (generate / migrate / db seed / studio).
  //
  // The datasource URL lives here, not in prisma/schema.prisma. It is read from
  // process.env directly rather than through Prisma's env() helper, because env()
  // throws while this file loads and would break `prisma generate` — which runs
  // from the `postinstall` script — on a fresh clone before `.env` exists or on a
  // CI/Vercel install step. Commands that need a database (migrate, db seed, db
  // push, studio) fail with Prisma's own "datasource.url property is required"
  // error when DATABASE_URL is unset.
  //
  // Prisma 7 does not load .env automatically, hence the dotenv import.
  import "dotenv/config";
  import { defineConfig } from "prisma/config";

  const databaseUrl = process.env.DATABASE_URL;

  export default defineConfig({
    schema: "prisma/schema.prisma",
    migrations: {
      path: "prisma/migrations",
      seed: "tsx prisma/seed.ts",
    },
    ...(databaseUrl ? { datasource: { url: databaseUrl } } : {}),
  });
  ```

  generator client {

    output   = "../generated/prisma"

    provider = "postgresql"
  }

  import { PrismaPg } from "@prisma/adapter-pg";
  import { env } from "~/env";
  import { PrismaClient } from "../../generated/prisma/client";

  /**
   * Prisma 7 requires an explicit driver adapter. node-postgres (`pg`, wrapped by
   * `@prisma/adapter-pg`) is used in every environment — Docker Postgres locally,
   * Neon / Vercel Postgres in production — over the standard DATABASE_URL string.

    prisma: ReturnType<typeof createPrismaClient> | undefined;

  if (env.NODE_ENV !== "production") globalForPrisma.prisma = db;

### 6. Edge Cases & Considerations

#### Edge Cases to Handle

1. **`pnpm install` with no `.env`** (fresh clone, CI, Vercel install step): `postinstall` → `prisma generate` must succeed. Guaranteed by the conditional `datasource` in `prisma.config.ts` (verified on 7.10.0: generate succeeds with the variable unset).
2. **`pnpm db:migrate` / `pnpm db:seed` / `pnpm db:push` with no `DATABASE_URL`**: Prisma prints `Error: The datasource.url property is required in your Prisma config file when using prisma migrate …` and exits non-zero. This is the intended, actionable failure.
3. **`DATABASE_URL` set but database down**: `prisma migrate deploy` fails with `P1001: Can't reach database server`; the app's first query fails likewise. Unchanged from Prisma 6.
4. **Vercel build**: Vercel injects `DATABASE_URL` into `process.env` (Production and, since 2026-09-15, Preview), so `dotenv/config` is a no-op and `prisma migrate deploy` in `build` works. `dotenv`, `prisma`, and `tsx` are devDependencies; Vercel installs devDependencies during the build. `prisma.config.ts` is only evaluated by the CLI, never by the deployed app. Vercel builds with pnpm 10.28 and Node 24.x, both compatible with `allowBuilds` and Prisma 7.
5. **Unit tests**: `vitest.config.mts` sets `SKIP_ENV_VALIDATION=1`; no test imports `~/server/db`, so no adapter is constructed during `pnpm test`. The new config test imports `prisma.config.ts` only, which has no database side effects. `pg` pools are lazy, so even importing `db.ts` would not open a connection.
6. **Raw SQL bigint columns**: `getSnapshot` in `src/server/campaignStats.ts` casts `SUM`/`COUNT` to `::bigint` and converts with `Number()`. The `pg` adapter maps `int8` to JS `bigint`, matching the existing `SnapshotRow` type; `Number()` would also coerce a string correctly, so the code is robust either way. No change to that file.
7. **Old pnpm in the implementation container**: pnpm 9 treats a `pnpm-workspace.yaml` without `packages` as an invalid workspace root. Phase 1's first step upgrades pnpm before anything else runs.
8. **`prisma migrate dev` shadow database**: needs the `CREATEDB` privilege on the role. The Phase 1 role creation grants it.

#### Potential Challenges

- ⚠️ **`prisma@latest` is an 8.0 release candidate**: never use `latest`, `@8`, or unpinned ranges. Exact-pin `7.10.0` for all three packages.
- ⚠️ **Generated client entry point moved**: the `prisma-client` generator emits TypeScript sources (`client.ts`, `models.ts`, `enums.ts`, …) rather than `index.js`/`index.d.ts`. Any import of `../../generated/prisma` (no suffix) fails to resolve. Only `db.ts` and `seed.ts` import it; both are updated.
- ⚠️ **Build cache on Vercel** may restore a `generated/` folder from a Prisma 6 build; the `build` script's leading `prisma generate` regenerates it, so no action is needed.

#### Security Considerations

- `DATABASE_URL` is read from the environment only; `prisma.config.ts` never logs it.
- Placeholder Clerk values used during local verification are format-valid dummies in the git-ignored `.env`; they are never committed.
- `pnpm-workspace.yaml#allowBuilds` approves build scripts only for the four named packages.
